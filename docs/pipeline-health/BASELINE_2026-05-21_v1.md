## Postmortem: the value-verification gap

Three review rounds verified column names, column types, cross-table schema asymmetries (`institution` vs `institution_code`), dual-writer columns, FULL OUTER JOIN semantics, `array_length` null handling, deprecated-status filter scope, and pack-promotion semantics. The views still shipped with `WHERE j.status = 'success'` against a column whose enum is `{completed, failed}`. Q1 and Q2 returned identically zero for every institution; Q3 understated UMGC's scrape volume by 145 rows.

The verification regime treated **column names as schema** (verified before use via `\d` / `information_schema`) and **string-literal values as world-facts** (used from memory). Both are observations about the database. Both require empirical verification.

**Checklist update for any future view review:**

1. Every column name in a SELECT or WHERE clause: confirm via `information_schema.columns`.
2. Every string literal in a WHERE / FILTER / CASE clause: confirm via `SELECT DISTINCT <col> FROM <table>`.
3. Hardcoded enum values in more than one place: extract to a helper function or shared CTE so the next rename touches one site. See `public._scrape_job_success_status()` for the pattern used here.

A view that filters on a non-existent string compiles fine and silently returns the empty set forever. The fix is value-verification, not more review rounds.
